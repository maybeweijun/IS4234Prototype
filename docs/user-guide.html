01 / SAFEGUARD

Open the assurance workspace

Safeguard helps an engineering owner and an independent reviewer manage release evidence, field concerns and corrective actions for a candidate Autosteer safeguard build. Open http://127.0.0.1:4234 while the local service is running. The prototype uses sample records and real transactions on an isolated local EVM. No wallet extension or paid network tokens are required.

Start or restart the service

npm ci
npm run build
npm run typecheck
npm test
npm start

Run these commands in the project directory with Node.js 24 on PATH; Node 24.22.2 was used for validation. Dependencies are already installed in the provided workspace. The first build may download Solidity 0.8.34. Keep the start terminal running, then open the local link. Stop with Ctrl+C. Restarting creates a fresh candidate and chain; export evidence before stopping.

Access model: role selection operates prototype test accounts held by the local service. It is not production authentication. Smart-contract role checks are real, but this interface intentionally permits switching between those test identities. The service binds only to loopback and has no vehicle connection.
02 / SAFEGUARD

Role workspaces and section meanings

The selected role changes which panels, controls and evidence samples are visible. A responsibility summary and recommended next step appear above the status cards. The role menu remembers the last selection in the current browser session. Views focus the workflow; the smart contract separately enforces transaction permissions.

WorkspaceVisible work
EngineerCandidate; laboratory evidence submission and coverage; assigned investigations; decision history; build revisions. No approval or closure controls.
Safety reviewer / Second reviewerCandidate; all required evidence; release judgments; independent action closure; decision history and review export. No evidence submission or build controls.
Field analystCandidate; field evidence and comparison results; safety concerns; investigation status. No laboratory table, release controls or action closure.

03 / SAFEGUARD

Validate the candidate and approve limited deployment

  1. Start with a fresh session. Confirm candidate autosteer-2026.1 and the HW3-enabled / HW4-enabled scope in section 01. The initial laboratory gate is Missing.
  2. Choose Engineer. In section 02 select Validation: complete scenario coverage, click Load sample and inspect the JSON. Submit evidence. Six transactions record three scenarios for each configuration.
  3. Read section 04. Each supplied result is 39 / 40 (97.5%) and should become Eligible for reviewer assessment. The field gate is still Missing; this does not prevent a laboratory-based limited decision.
  4. Confirm that the Engineer workspace has no release-approval controls. The scripted workflow and automated tests separately verify that a direct self-approval request is rejected by the contract. Switch to Safety reviewer for a decision.
  5. Switch to Safety reviewer. Explain which evidence was reviewed, the remaining uncertainty and why the limited decision is justified. Select a validity period of 1, 7 or 30 days, then Approve limited deployment.
  6. Confirm stage Limited, effective authority Limited only, and a DecisionRecorded event. The field gate remains separate. Preserve the original rationale and snapshot in the exported review package.

Inspect negative evidence cases

On a fresh session, edit one laboratory record before submitting: remove a required record to leave Missing coverage; reduce trials to 29 for Inconclusive; set 37 successes out of 40 for Failed; or change the build label to exercise a rejected stale import. A later build revision makes already-recorded results Stale. A reviewer cannot approve until every required laboratory result is eligible.

Rationale example:
Reviewed current-build evidence for all required scenarios
and configurations. Record the residual uncertainty and
monitoring conditions supporting limited deployment.
The service requires a meaningful rationale of 10-2,000 characters. The contract requires a non-zero rationale hash and a validity window no longer than 30 days. Neither check evaluates the quality of the reviewer's reasoning. In a real workflow, rationale documents must be retained and independently inspectable.
04 / SAFEGUARD

Monitor field evidence and escalate concerns

  1. After a limited decision, switch to Field analyst. Load Monitoring: adverse event trend and submit it. The HW3 sample compares 8 events / 4,000 miles with 12 / 4,000 miles.
  2. Read the field card: 2.000 becomes 3.000 events per 1,000 engaged miles. Stage becomes Reopened, effective authority becomes unavailable, and section 05 shows Action 1 assigned to the engineer with a seven-day deadline.
  3. Try Approve expansion in the Safety reviewer workspace while the action is open. The request is rejected. Missing HW4 field data would also need to be supplied before expansion can become eligible.
  4. Switch to Safety lead and open Prototype clock controls in section 05. Use Advance review clock 8 days. This control changes only the simulated EVM clock. Action 1 becomes Overdue; prior decisions may also have expired.
  5. With action ID 1 selected, click Escalate overdue action. Any participant may submit this transaction. Confirm the escalated flag and ActionEscalated event. No email, vehicle command or external notification is sent.
  6. Switch to Field analyst. Load Monitoring: follow-up evidence and submit both records. The field gate becomes eligible, but Action 1 remains open until independently closed.

Use Monitoring: insufficient exposure in a separate fresh run to see an Inconclusive field result rather than a false pass. In edited JSON, complete:false or comparable:false also remains inconclusive. An inactive safeguard or serious-event flag fails even when cohort quality is poor.

Every non-eligible field submission creates an action. Repeated submissions can therefore create multiple open actions, all of which must receive independent disposition. Improved measurements never automatically close earlier concerns.
05 / SAFEGUARD

Close actions, record a new decision and revise builds

  1. Inspect the investigation and improved source evidence. Choose Safety reviewer, set the action ID, and enter a resolution summary in section 05. Enter the Independent closure rationale in section 05.
  2. Click Close action independently. The reviewer cannot be the action's reporter, owner or any candidate data contributor. If the primary reviewer originally reported the concern, use Second reviewer for closure.
  3. Confirm the action is Closed and open-action count is zero. The closure itself does not grant deployment authority. A failed or missing evidence gate still blocks expansion.
  4. Provide a new release rationale and click Approve expansion. Confirm Expansion authorized and a second snapshot decision. This is the required separate release judgment.
  5. To test reassessment, choose Engineer. Enter a revision rationale, keep or change the new build label autosteer-2026.2, then click Revise candidate build.
  6. Confirm Reopened and Stale laboratory/field evidence, with earlier decisions still listed. Load the laboratory sample and edit its build to the new label before submitting. The new build needs its own limited decision before field evidence can be recorded.

Understand recorded stage versus current authority

A Limited or Expanded label records the last judgment, but expiry or reviewer-role revocation can remove its current effect. Always use the Deployment authority card and the contract's isDeploymentAuthorized query for operational eligibility. Evidence changes and action closure conservatively reopen review even when the new data improve.

Respect fixed scope

The current interface works with one initialised candidate and its two fixed configurations. The contract supports multiple candidates and up to eight configurations each. To change scope or add configurations, create a new candidate through an integration or script; do not relabel existing evidence. Build revisions preserve the original scope.

Do not interpret a revoked decision as an automatic rollback. This prototype governs evidence and authorisation records. It does not disable an installed feature, send an OTA package or change vehicle behaviour.
06 / SAFEGUARD

Export, verify and reconstruct a review

In the Safety reviewer, Safety lead or Auditor / observer workspace, use Export review package to download safeguard-review.json at any stage. The package includes the current candidate and policy hash, all current evidence summaries, historical decisions, open and closed actions, canonical preimages, raw event topics/data, block identifiers and transaction hashes. Browser exports also include a clearly labelled off-chain request activity log.

Run the reproducible command-line workflow

npm run demo
npm run verify:evidence

# PowerShell: verify another exported package
$env:REVIEW_FILE = 'C:/path/to/safeguard-review.json'
npm run verify:evidence

The scripted run uses its own isolated chain. It saves output/demo/review-expanded.json, review-reopened.json and walkthrough.json. The first package captures a separately approved expansion. The second captures a new build whose evidence is stale while both earlier decisions remain. The walkthrough records observed blocked attempts and successful transitions.

Reconstruction checkEvidence to inspect
What was reviewed?Build and scope hashes; ordered configurations; current and historical LabRecorded / FieldRecorded inputs.
Who decided, when and why?Decision reviewing address, decidedAt, validity window, snapshot and rationale hash; corresponding canonical rationale text.
Why did review reopen?Evidence revisions, BuildRevised / ReviewReopened / ActionOpened events and subsequent closure records.
Was content altered?Recompute Keccak-256 of retained canonical UTF-8 preimages; independently recompute the snapshot using ABI encoding.
Was the ledger authentic?Compare chain identity, approved contract address, transaction inclusion and event data with a trusted node or archived chain. A self-consistent JSON file alone does not establish provenance.
The verification command checks internal package fingerprints, the current snapshot and historical evidence preimages. It does not validate measurement truth or independently prove blockchain inclusion. Local chain state is discarded at shutdown; retain exports, and use persistent independently governed infrastructure for operational assurance.

Rejected transaction estimates do not produce confirmed contract events. The local request log helps explain those attempts but is not a tamper-resistant audit source. Earlier successful transactions in a multi-record import are not rolled back if a later record fails.

Automated results: 56 passing tests, including 45 new Solidity tests and six new integration tests. The retained Counter sample contributes five tests. Rate-comparison fuzzing executed 256 cases in its test. The browser workflow was separately exercised on the local service. These results demonstrate implemented workflow behaviour; no participant study or vehicle safety result was conducted.

Suggested walkthrough sequence

  1. 0:00-0:45: Explain the evidence-to-accountability gap. Show missing coverage and a blocked decision.
  2. 0:45-1:40: Submit six lab records, show that engineer approval controls are absent, then record an independent limited decision.
  3. 1:40-2:40: Submit adverse field evidence. Explain the 2.0 to 3.0 rate increase, reopened review and owned action.
  4. 2:40-3:40: Advance time, escalate, submit follow-up data and show that the action stays open.
  5. 3:40-5:00: Close independently, approve expansion separately, revise the build and export the preserved decision history.

Troubleshooting and developer reference

SymptomAction
Page does not loadKeep npm start running and open the printed loopback URL. If port 4234 is occupied, use another PORT value and the matching URL.
UnauthorizedUse Engineer for laboratory/build changes, Analyst for field data, and Reviewer for release/closure judgments. Observer has no evidence write permission.
SeparationOfDutiesUse a reviewer who never contributed candidate data. A concern's reporter also cannot close that action; SecondReviewer is available.
GateBlocked or OpenActionsRead every configuration row and field explanation. Supply current evidence, investigate concerns, close actions independently and make a separate decision.
Wrong build / stale evidenceMatch the exact current build label in JSON. Existing data from an earlier build revision cannot satisfy the current build, even if an old label is reused.
New-build field import rejectedFirst submit the new build's laboratory results and obtain its own limited decision.
Overdue escalation rejectedEscalation requires time strictly after the due date and an open, not-yet-escalated action.
Old labels remain in an open browserRefresh the page and chain state after a service restart. Candidate metadata is loaded at session creation; changing a source JSON file does not rewrite existing chain state.

Repository map

contracts/SafeguardAssurance.sol contains the workflow. contracts/SafeguardAssurance.t.sol holds unit and fuzz tests. test/SafeguardAssurance.ts covers off-chain orchestration. scripts/lib/prototype.ts defines validation, canonical hashes and exports; scripts/serve.ts hosts the local workspace. data/ contains sample inputs; web/ contains the interface. ignition/modules/SafeguardAssurance.ts supplies a declarative deployment module. The original Counter example is retained separately.

Documentation and deployment

The solution design explains GRC fit, users, rules and implementation limits. Six editable PlantUML sources and rendered SVG views are in docs/uml/. Documentation source is docs/content.json; scripts/build-docs.py regenerates HTML and PDF outputs with the packages in docs/requirements-docs.txt. The application itself needs no Python.

npx hardhat ignition deploy `
  ignition/modules/SafeguardAssurance.ts `
  --network hardhatMainnet
The Ignition module deploys the contract with account 0 as safety lead; it does not seed roles or a candidate. The browser service and scripted workflow initialise their own independent simulated chain. Production deployment requires separately designed authentication, evidence storage, network governance, recovery and release-system enforcement.
